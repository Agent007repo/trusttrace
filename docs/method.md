# Method

We treat TrustTrace as a design-oriented artefact study. Problem investigation uses public project information and explicitly authored stakeholder concerns. Treatment design creates a typed chain from concern to requirement, six-part scenario, decision, component and test. Treatment validation begins with adversarial software scenarios, followed by the pre-registered elicitation comparison and, later, a practitioner study.

An architect first identifies the trustor, trustee, entrusted action and required evidence. A concern becomes a requirement only when its fit criterion can fail. For every conflict, we list the affected requirements, compare options, record the decision and retain the residual cost. An architecture decision record (ADR) includes a reflection on assumptions and stakeholder disagreement.

We use the six-part scenario fields specified on page 19 of the opened SEI presentation linked in the source register. Our scenarios use original case wording; no workshop has been conducted. Wieringa's publisher page verifies the methodological reading target; full-text synthesis remains pending. The opened Hevner abstract supports the artefact-building orientation; it does not establish that we have satisfied every design-science guideline.

Source provenance is part of the model. A synthetic concern cannot become empirical interview evidence merely because a test passes. The source register preserves legal retrieval failures. Specific ISO/IEC 25010:2023 mappings remain unverified rather than copying an older taxonomy.
